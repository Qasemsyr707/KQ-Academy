## ما يتضمنه الإصدار

- **صلاحيات المدراء التفصيلية:**
  - 15 صلاحية، يتحكم بها المالك لكل مدير على حدة من صفحة `/admin/permissions`.
  - مجموعات جاهزة، وسجل تغييرات.
  - كل صلاحية تُفحص على الخادم.
  - المدراء الحاليون يحتفظون بكل صلاحياتهم. أما المدير الجديد فيبدأ بلا صلاحيات حتى يمنحه المالك.
- **تعديل المدرب لكورس منشور:**
  - من صفحة «تعديل الكورس» يرسل المدرب طلب تعديل للعنوان أو الغلاف أو الوصف أو التصنيف أو المدة أو السعرين أو فيديو المقدمة أو الميزات.
  - الطلب يُحفظ معلقاً، والكورس المنشور لا يتغيّر.
  - تراجعه الإدارة في `/admin/course-requests`، مع مقارنة القيمة الحالية بالمقترحة.
  - الموافقة تطبّق التعديل كاملاً دفعة واحدة. الرفض يتطلب سبباً يظهر للمدرب.
  - لا يراجع أحد طلبه بنفسه، والموافقة المكررة مرفوضة.
  - إذا تغيّر الكورس بعد إرسال الطلب، تُرفض الموافقة عليه حتى لا يُكتب فوق التغيير الجديد.
- **مراجعة الكورسات الجديدة:**
  - كورس المدرب يبدأ مسودة، ثم يرسله المدرب للمراجعة.
  - تنشره الإدارة بعد تحديد السعر المعتمد صراحةً.
- **Phase 1:**
  - إشعارات فعلية بلا تكرار.
  - تقدّم الطالب محفوظ على الخادم.
  - الشهادة تصدر عند إكمال جميع الدروس.
  - رابط تحقق من الشهادة لا يمكن تخمينه.
  - تنزيل الشهادة محمي.
- **Phase 2:**
  - تصنيفات المهارات: 24 تصنيفاً رئيسياً و116 فرعياً.
  - بحث متقدم.
  - رفع Bunny قابل للاستكمال بعد الانقطاع.
  - أغلفة الكورسات بنسبة 16:9.

## تحديث قاعدة البيانات

يتم تلقائياً عند تشغيل الحاوية الجديدة، عبر `scripts/release-migrate.cjs`، قبل أن تستقبل أي طلب.

1. **تسجيل الـ baseline:** إذا لم يكن الـ baseline مسجلاً، يقارن السكربت القاعدة بمخطط Production (`prisma/baseline/production-20261120.prisma`).
   - إذا تطابقا، يسجّل الـ baseline كمطبَّق **دون تنفيذه**.
   - إذا اختلفا، يتوقف ولا يغيّر شيئاً، ولا يبدأ التطبيق.
2. **التطبيق:** يشغّل `prisma migrate deploy`، فيطبّق الإضافات التالية:
   - Phase 1: عمود `dedupeKey`، وجدول `LessonProgress`.
   - Phase 1b: `verifyToken`، و`durationHours`.
   - Phase 2: جدول `Category`، و`categoryId` و`tags` و`trainingType`، وربط الكورسات الحالية بالتصنيفات حين يكون الربط مؤكداً فقط.
   - صلاحيات المدراء.
   - طلبات التعديل.
3. **إعادة التشغيل:** في كل تشغيل لاحق لا يُطبَّق شيء إن لم يوجد جديد.

جُرّب ذلك على نسخة محلية معزولة بمخطط Production، وكانت النتيجة:

- **البيانات:** لم تتغيّر. البصمة قبل التطبيق وبعده متطابقة.
- **المخطط:** يطابق `schema.prisma` تماماً.
- **التشغيل الثاني:** لم يغيّر شيئاً.
- **الصلاحيات:** إذنٌ سحبه المالك لم يرجع بعد إعادة التشغيل.
- **القاعدة المختلفة:** توقف السكربت دون أي تعديل.

الكود القديم يعمل على المخطط الجديد، لأن كل الإضافات أعمدة يقبل فيها `NULL`، أو لها قيمة افتراضية، أو جداول جديدة.

## خطوات النشر

### 1. اكتشاف القاعدة الفعلية (قراءة فقط)

من Coolify افتح **Servers ← الخادم ← Terminal**، ثم الصق:

```sh
docker ps --format '{{.Names}}\t{{.Image}}\t{{.Status}}' | grep -iE 'postgres|kq|academy'
```

بعدها افتح حاوية تطبيق الإنتاج بالاسم الذي ظهر، واعرض عنوان القاعدة بعد إخفاء كلمة المرور:

```sh
docker exec <app-container> sh -c 'printenv DATABASE_URL' | sed -E 's#//[^@]*@#//***@#'
```

يظهر في الناتج اسم مضيف القاعدة واسمها.

### 2. نسخة احتياطية قابلة للاسترجاع (إلزامية)

نفّذ الأوامر من Terminal الخادم نفسه:

```sh
PG=<postgres-container>; DB=<database-name>; D=/root/kq-backups/prod-20261121; mkdir -p $D
docker exec $PG sh -c "pg_dump -U \"\$POSTGRES_USER\" -d $DB -Fc" > $D/kqacademy.dump && ls -lh $D/kqacademy.dump
docker exec -i $PG pg_restore --list < $D/kqacademy.dump | grep -c 'TABLE DATA'
sha256sum $D/kqacademy.dump | tee $D/kqacademy.dump.sha256
```

اختبار استرجاع كامل في قاعدة مؤقتة، ثم حذفها (موصى به):

```sh
docker exec $PG sh -c "createdb -U \"\$POSTGRES_USER\" kq_restore_check"
docker exec -i $PG sh -c "pg_restore -U \"\$POSTGRES_USER\" -d kq_restore_check --no-owner" < $D/kqacademy.dump
docker exec $PG sh -c "psql -U \"\$POSTGRES_USER\" -d kq_restore_check -Atc 'select count(*) from \"User\"'"
docker exec $PG sh -c "psql -U \"\$POSTGRES_USER\" -d $DB -Atc 'select count(*) from \"User\"'"
docker exec $PG sh -c "dropdb -U \"\$POSTGRES_USER\" kq_restore_check"
```

يجب أن يتطابق الرقمان في السطرين الثالث والرابع.

### 3. الدمج والنشر (بعد تأكيد النسخة الاحتياطية)

1. ادمج `release/production-20261121` في `main`. الدمج fast-forward، لأن `main` الحالي هو أصل الفرع.
2. اضغط **Deploy** على تطبيق Coolify الحالي، أو انتظر النشر التلقائي إن كان مفعّلاً.
3. لا يتغير شيء آخر: النطاقات ومتغيرات البيئة والقاعدة تبقى كما هي.

### 4. التحقق

- **سجل النشر:** يظهر فيه `[release-migrate] database is up to date`، ثم يبدأ `next start`.
- **فحص الصحة:** Healthcheck الحالي في Coolify يعود بـ 200.

## التراجع

- **الكود:** أعد نشر `rollback/prod-before-20261121` (أي `131f8e0`). يعمل على المخطط الجديد كما هو، ولا يلزم حذف أي إضافة.
- **القاعدة:** لا يلزم تراجع. في حالة كارثية فقط تُسترجع النسخة الاحتياطية من الخطوة 2 بـ `pg_restore --clean`. هذا يحذف أي بيانات أُضيفت بعد النسخة، فهو آخر الحلول.
