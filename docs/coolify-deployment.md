# نشر KQ Academy باستخدام GitHub وHostinger VPS وCoolify

هذا دليل إعداد ومراجعة، ولا ينفّذ أي تغيير في الخادم. البنية المعتمدة هي
GitHub للكود، وCoolify على Hostinger VPS للبناء والتشغيل، وPostgreSQL على الخادم،
وBunny Stream للفيديو. تبقى بيانات المصادقة والتخزين والتكاملات الحالية محفوظة.

## مصدر الكود وأوامر التطبيق

اختر المستودع `Qasemsyr707/KQ-Academy` والفرع الذي تمت مراجعته في تطبيق Coolify.
يكون Base Directory هو جذر المستودع الذي يحتوي `package.json`؛ اسم نسخة العمل
المحلية `kqacademy-pdf-attachments` ليس مجلداً داخل المستودع المنشور.
راجع النشر التلقائي والـ webhooks قبل ربط فرع جديد؛ هذا التعديل لا يغيّرها.

لإعداد Coolify باستخدام Nixpacks، راجع الأوامر التالية في إعدادات التطبيق:

| الإعداد | القيمة |
| --- | --- |
| Install Command | `npm ci --include=dev` |
| Build Command | `npm run build` |
| Start Command | `npm start -- --hostname 0.0.0.0 --port 3000` |
| المنفذ الداخلي | `3000` |
| نوع التطبيق | خادم Node.js، وليس Static أو SPA |

الأوامر موجودة في المشروع ولا تحتاج إلى سكربت نشر خاص. يحتفظ دليل الإعداد
بـ Nixpacks عند استخدامه حالياً؛ تغيير أداة البناء قرار منفصل يحتاج اختباراً.
تحتاج مرحلة البناء إلى Prisma CLI وTypeScript من `devDependencies`، ولذلك
يتضمن أمر التثبيت أدوات التطوير حتى عند ضبط `NODE_ENV=production`.
اختر إصدار Node.js مدعوماً ومتوافقاً مع الحزم، وثبّت اختياره في Coolify؛ يمكن
ضبط `NIXPACKS_NODE_VERSION` عند استعمال Nixpacks. الحد الأدنى في Next.js المثبت
هو Node.js 20.9.0، ويجب مراعاة متطلبات بقية الحزم أيضاً.

يجب أن يجري تثبيت الحزم و`prisma generate` على Linux داخل البناء، لا بنقل
`node_modules` أو `.next` من Windows. لا يلزم تغيير `next.config.ts` أو حذف
حزم Next.js الداخلية لتشغيل `next start`.

## البيئة وقاعدة البيانات

انقل القيم المعتمدة إلى إعدادات البيئة في Coolify دون تغيير المفاتيح أو نشرها
في Git. القائمة التالية توضح المتغيرات المرتبطة بالتشغيل، وليست مبرراً لحذف
أي متغير موجود وغير مذكور:

| المتغير | الاستخدام والنطاق |
| --- | --- |
| `DATABASE_URL` | PostgreSQL؛ مطلوب أثناء البناء والتشغيل حالياً |
| `NEXTAUTH_URL` | عنوان المنصة العام عبر HTTPS في بيئة التشغيل |
| `NEXTAUTH_SECRET` | سر المصادقة الحالي؛ يبقى ثابتاً وسرياً على السيرفر |
| `NEXT_PUBLIC_APP_URL` | عنوان المنصة العام؛ متاح أثناء البناء والتشغيل |
| `BUNNY_LIBRARY_ID`, `BUNNY_API_KEY` | المكتبة ومفتاحها؛ على السيرفر أثناء التشغيل |
| `BUNNY_STREAM_TOKEN_AUTH_KEY`, `BUNNY_STREAM_TOKEN_AUTH_ENABLED` | إعدادات توقيع المشغل الحالية، عند استخدامها، على السيرفر فقط |
| `BUNNY_UPLOAD_STATE_DIR` | مسار سجلات رفع الفيديو الدائمة |
| `DOCUMENT_STORAGE_DIR` | مسار المرفقات الخاصة الدائم |
| `DOCUMENT_LEGACY_STORAGE_DIR` | مسار الأصول القديمة عند استخدام هذا المسار |
| `CRON_SECRET` | حماية مهمة التذكيرات إذا كانت مفعلة |

تبقى متغيرات الخدمات المستخدمة، مثل LiveKit وGemini والبريد والدفع وImgBB
و`JWT_SECRET`، بقيمها الحالية. تحتفظ المنصة بتحليلات Google عند إعداد
`NEXT_PUBLIC_GA_ID`؛ لا يتطلب ذلك خدمة استضافة معينة.

متغيرات `NEXT_PUBLIC_*` تصبح جزءاً من حزمة المتصفح وقت البناء، فلا تضع مفاتيح
سرية ضمنها، وأعد البناء بعد تغيير قيمها. لا تمنح أسرار التشغيل نطاق البناء
إلا عند الحاجة. استخدم آلية أسرار البناء المتاحة في Coolify للبيانات الحساسة
اللازمة للبناء، وراجع عدم ظهورها في سجلاته.

تولّد `/curriculum` صفحات من Prisma أثناء `next build`. يجب أن يستطيع عامل
البناء الوصول إلى قاعدة مخصصة لبيئته، بالإضافة إلى اتصال حاوية التشغيل بها.
قد لا تتوفر شبكة PostgreSQL أو اسم خدمتها الداخلي لعامل Docker build حتى
عندما يعمل الاتصال من حاوية التطبيق؛ إتاحة المتغير وقت البناء وحدها لا تثبت
إمكانية الوصول. اختبر ذلك على Linux باستخدام قاعدة تحقق مستقلة عن الإنتاج.
عنوان PostgreSQL داخل شبكة الحاويات ليس `localhost` إلا إذا كان الخادم في
الحاوية نفسها. راجع عنوان الخدمة والشبكة الفعليين في Coolify؛ لا تستبدل
اتصال الإنتاج أو تنشئ قاعدة جديدة ضمن هذا التنظيف.

غياب `DATABASE_URL` يوقف استعلام الصفحة أثناء prerender، وليس `prisma generate`
أو تجميع Webpack. لا يكفي عنوان وهمي لتجاوز هذه الخطوة، ولا يلزم تحويل الصفحة
إلى `force-dynamic` ضمن تنظيف الاستضافة. صورة الاختبار المبنية على قاعدة تحقق
قد تحتوي بياناتها في الصفحات المولدة؛ لا تعتمدها كصورة إنتاج. عند النشر الفعلي،
يجب أن تتطابق بيانات البناء والتشغيل مع البيئة المستهدفة وفق إعدادات تمت مراجعتها.

لم يتغير مخطط Prisma ولا توجد Migration مطلوبة هنا. لا تضف `db:push` أو
`prisma migrate` إلى Build أو Start أو pre-deployment لهذا التعديل.

## التخزين الدائم

راجع التخزين الموجود قبل إضافة Volume جديد؛ ربط Volume فارغ لا ينقل ملفات
الحاوية السابقة. استخدم مسارات حاوية فعلية وصلاحيات تسمح لمستخدم التطبيق
بالكتابة، مع نسخة احتياطية من البيانات الحالية.

| البيانات | الوجهة داخل الحاوية | إعداد التطبيق |
| --- | --- | --- |
| المرفقات الخاصة وأوصافها | `/data/kq-documents` | `DOCUMENT_STORAGE_DIR=/data/kq-documents` |
| سجلات عمليات رفع Bunny | `/data/bunny-uploads` | `BUNNY_UPLOAD_STATE_DIR=/data/bunny-uploads` |
| صور الرفع المحلية القديمة، إن وجدت | مجلد `public/uploads` ضمن مسار العمل الفعلي | احتفظ بمحتواه وVolume الخاص به |
| أصول المستندات القديمة، إن وجدت | المسار الخاص المثبت فعلياً | `DOCUMENT_LEGACY_STORAGE_DIR` بالقيمة المطابقة |

اجعل تخزين المستندات منفصلاً عن سجلات Bunny وخارج `public` ودليل إصدار
التطبيق؛ التحقق الحالي يرفض المسارات غير الآمنة في الإنتاج. سجلات Bunny
صغيرة ولا تحتوي الفيديو نفسه، لكنها ضرورية لمنع إنشاء فيديو مكرر عند الاستكمال.
لا تثبّت Volume فوق كامل `public` أو كامل دليل التطبيق لأنه قد يحجب ملفات الصورة.
راجع [تفاصيل حماية المرفقات](pdf-attachments-repair.md) و[حالة الرفع](bunny-upload-repair.md).

يجب أن ترى جميع نسخ التطبيق البيانات الدائمة نفسها؛ Volumes محلية مستقلة
على خوادم مختلفة لا تحقق ذلك. تبقى بيانات PostgreSQL في التخزين الدائم
الخاص بقاعدة البيانات، مع نسخ احتياطية مناسبة لقاعدة البيانات.

## الفيديو والمصادقة والمهام

يستمر رفع الفيديو من المتصفح مباشرة إلى Bunny؛ لا يُحوّل الملف إلى حاوية
التطبيق. يستمر حفظ `Lesson.videoUrl` وربط الفيديو الموجود والتحقق من جاهزيته
وصلاحيات المشاهدة دون تغييرات. حافظ على مكتبة Bunny ومفاتيحها وقيود النطاق
والتوكن الحالية؛ لا تفعّل توكن المكتبة أو تغيّر مفتاحها ضمن نقل الاستضافة.
راجع [دليل مصادر الفيديو](lesson-video-sources.md) قبل أي تغيير لحماية المكتبة.

احتفظ بنطاق المنصة وHTTPS وإعدادات تمرير host/protocol من proxy كما هي حتى
تتطابق مع `NEXTAUTH_URL`، ولا تستبدل سر المصادقة. حافظ على سياسة iframe
الحالية التي تسمح فقط بمضيفي Bunny المعتمدين. يجب أن يحترم proxy ترويسات
`Cache-Control` و`CDN-Cache-Control`، وألا يخزّن ردود المصادقة والمرفقات الخاصة
وردود تشغيل الفيديو المشترطة بصلاحيات في cache مشترك. راجع حد حجم الطلب
ليستوعب مستنداً بحجم 20 MiB مع ترويسات multipart.

إذا كانت التذكيرات مفعلة، أعد إعداد جدولها في Coolify بنفس التوقيت والتكرار
المعتمدين لاستدعاء `POST /api/cron/reminders` مع `Authorization: Bearer <CRON_SECRET>`.
لا تضع السر في الكود أو السجلات، ولا تشغّل المهمة كاختبار لأنها ترسل رسائل.

## التحقق قبل النشر المراجع

1. شغّل `npm test` و`npm run typecheck` و`npm run lint` و`npm run build` في بيئة تحقق.
2. أكمل البناء على Linux مع قاعدة تحقق متاحة؛ نجاح التجميع وحده لا يثبت نجاح
   فحص الأنواع، لأن `ignoreBuildErrors: true` إعداد موجود مسبقاً في المشروع.
3. تحقّق على staging من تسجيل الدخول وصلاحيات الدروس المدفوعة ورفع فيديو
   واستكماله وربط فيديو موجود، دون إنشاء فيديو عند الربط.
4. افتح PDF ونزّله بحساب مصرح، وارفض الوصول من حساب غير مصرح، ثم تحقق من بقاء
   الملفات وسجلات الرفع بعد استبدال حاوية staging.
5. راجع الفرع والبيئة والمجلدات الدائمة قبل أي نشر؛ لا يتضمن هذا التنظيف Push
   أو Deploy أو تعديل الربط الخارجي أو Migration.

مراجع إعداد Coolify: [أوامر Nixpacks](https://coolify.io/docs/applications/builds/nixpacks/overview)،
[نطاق متغيرات البيئة](https://coolify.io/docs/applications/configuration/environment-variables)،
[Volumes الدائمة](https://coolify.io/docs/core/persistent-storage/storage-mounts/volume-mounts).
